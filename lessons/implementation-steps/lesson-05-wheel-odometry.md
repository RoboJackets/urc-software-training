# Lesson 5 Implementation - Wheel Odometry From Scratch

Build the `wheel_odometry` package from scratch. This is the first major C++ ROS 2
node students write in the course.

The data flow for this package is:

```text
/joint_states (wheel angles) -> WheelOdometry -> /wheel/odometry (pose + velocity)
```

In ROS terms, the package contains one **node**, the node has one **subscription**
and one **publisher**, and a **launch file** starts the node with simulation time.

## Create The Package

From `/workspace/src` in a TigerVNC terminal:

```sh
ros2 pkg create wheel_odometry --build-type ament_cmake --dependencies \
  rclcpp rclcpp_components sensor_msgs nav_msgs geometry_msgs tf2 tf2_geometry_msgs \
  robonav_training_common
```

Create these files:

```text
src/wheel_odometry/include/wheel_odometry/wheel_odometry.hpp
src/wheel_odometry/src/wheel_odometry.cpp
src/wheel_odometry/launch/wheel_odometry.launch.py
```

Do not add the C++ target to `CMakeLists.txt` until the header and source skeletons
exist.

The command creates `package.xml` and `CMakeLists.txt` for you. The dependency
list tells ROS which message types and libraries this package needs; it does not
create the node itself. Run the command from `/workspace/src`, but edit the new
files under `/workspace/src/wheel_odometry`.

Build the generated empty package once before writing C++:

```sh
cd /workspace
colcon build --packages-select wheel_odometry
```

The creation command adds the C++ dependencies to `package.xml`. Verify it has
these entries, then add the two launch-time dependencies:

```xml
<buildtool_depend>ament_cmake</buildtool_depend>

<depend>rclcpp</depend>
<depend>rclcpp_components</depend>
<depend>sensor_msgs</depend>
<depend>nav_msgs</depend>

<exec_depend>launch_ros</exec_depend>
```

These lines belong inside `<package>...</package>`; do not create a second XML
root or duplicate dependencies already generated by `ros2 pkg create`.

## Recommended Build Checkpoints

Do not attempt the whole package before compiling. Use these checkpoints:

1. **Empty generated package:** run the build immediately after `ros2 pkg create`.
2. **Class skeleton:** create the header and source, define the constructor and
   both methods with temporary no-op bodies, register the component, wire CMake,
   and build again.
3. **ROS plumbing:** declare parameters and create the publisher/subscriber. Keep
   the callback body empty and build again.
4. **Input handling:** add the provided joint lookup, array-length check,
   first-message baseline, and timestamp guard. Build again.
5. **Odometry math:** add wheel deltas, midpoint integration, and velocities.
   Build again.
6. **Output message:** fill the odometry fields, quaternion, covariance, and
   publish call. Build, source, and run the acceptance checks.

Temporary no-op method bodies for checkpoint 2 can look like this:

```cpp
void WheelOdometry::onJointState(
  const sensor_msgs::msg::JointState::SharedPtr msg)
{
  (void)msg;
}

void WheelOdometry::publishOdometry(
  const rclcpp::Time & stamp, double vx, double wz)
{
  (void)stamp;
  (void)vx;
  (void)wz;
}
```

Remove the matching `(void)` lines when you begin using those arguments.

## Header Requirements

Write a `WheelOdometry` class that inherits from `rclcpp::Node`.

Include member state for:

- parameters: `wheel_radius`, `wheel_separation`, `left_joint_name`,
  `right_joint_name`
- subscriber for `/joint_states`
- publisher for `/wheel/odometry`
- integrated pose: `x`, `y`, `theta`
- previous wheel positions and previous timestamp
- a boolean for whether the first valid joint message has arrived

Declare private methods:

- `onJointState(...)`
- `publishOdometry(...)`

Use the message types in the member declarations, not generic ROS types:

- `rclcpp::Subscription<sensor_msgs::msg::JointState>::SharedPtr`
- `rclcpp::Publisher<nav_msgs::msg::Odometry>::SharedPtr`

Initialize numeric state to zero and the first-message flag to `false`. Keep the
callback and publisher helper private because only ROS callbacks inside this node
need to call them. The constructor remains public so ROS can create the component.

A useful header scaffold is:

```cpp
class WheelOdometry : public rclcpp::Node
{
public:
  explicit WheelOdometry(const rclcpp::NodeOptions & options);

private:
  void onJointState(const sensor_msgs::msg::JointState::SharedPtr msg);
  void publishOdometry(const rclcpp::Time & stamp, double vx, double wz);

  double x_{0.0};
  double y_{0.0};
  double theta_{0.0};
  bool have_prev_{false};

  // TODO: parameters, previous measurements, publisher, and subscription
};
```

## Node Requirements

In the constructor:

- declare parameters with defaults from the URDF: radius `0.075`, separation `0.34`
- use joint names `left_wheel_joint` and `right_wheel_joint`
- subscribe to `/joint_states`
- publish `nav_msgs/msg/Odometry` on `/wheel/odometry`

`declare_parameter` both supplies a default and allows a launch file to override
it later. Store the returned value in the matching member. Create the publisher
and subscription with queue depth `10`; bind the subscription callback to `this`
using `std::bind` and `std::placeholders::_1`.

For example, the subscription follows this ROS 2 pattern:

```cpp
joint_sub_ = create_subscription<sensor_msgs::msg::JointState>(
  "/joint_states", 10,
  std::bind(&WheelOdometry::onJointState, this, std::placeholders::_1));
```

If this does not compile, make sure `<functional>` is included and the callback
signature in the header exactly matches the definition in the source file.

Finding wheel positions:

- `/joint_states.name` is a list of joint names
- `/joint_states.position` is the matching list of positions
- find the indices for `left_joint_name` and `right_joint_name`
- ignore a message if either joint is missing

Use this provided helper; joint-name lookup is ROS message bookkeeping rather than
the odometry idea this lesson is testing:

```cpp
static int findJointIndex(
  const sensor_msgs::msg::JointState & msg, const std::string & joint_name)
{
  for (std::size_t index = 0; index < msg.name.size(); ++index) {
    if (msg.name[index] == joint_name) {
      return static_cast<int>(index);
    }
  }
  return -1;
}
```

Call it for both configured wheel names. If either result is negative, return
from the callback. Before reading `position`, use the larger index to verify the
array is long enough:

```cpp
const int left_index = findJointIndex(*msg, left_joint_name_);
const int right_index = findJointIndex(*msg, right_joint_name_);
if (left_index < 0 || right_index < 0) {
  return;
}

const std::size_t largest_index =
  static_cast<std::size_t>(std::max(left_index, right_index));
if (largest_index >= msg->position.size()) {
  return;
}

const double left_position =
  msg->position[static_cast<std::size_t>(left_index)];
const double right_position =
  msg->position[static_cast<std::size_t>(right_index)];
```

Do not assume that the left wheel is always element 0. ROS does not guarantee the
ordering of a `JointState`.

## Odometry Math

On the first valid joint message, store the wheel positions and timestamp, publish a
zero odometry message, and return.

On later messages, students implement:

- wheel deltas in radians
- ground distances `d_left` and `d_right`
- `d_center = (d_left + d_right) / 2`
- `d_theta = (d_right - d_left) / wheel_separation`
- midpoint integration using `theta + d_theta / 2`
- angle normalization with `robonav_training_common::normalizeAngle`
- velocities from `d_center / dt` and `d_theta / dt`, guarded by `dt > 0`

Implement the callback in this order:

1. Find both joint indices and read the two positions.
2. Convert `msg->header.stamp` to `rclcpp::Time`.
3. If this is the first usable message, save it as the baseline and return after
   publishing zero velocity. A single encoder reading cannot produce a delta.
4. Compute `dt`. Ignore duplicate or out-of-order timestamps before changing
   either the pose or the saved baseline.
5. Convert each angular change to meters with `distance = angle_change * radius`.
6. Integrate `x`, `y`, and `theta`, then publish.
7. Only after publishing, save the current wheel positions and time for the next
   callback.

For midpoint integration, update position with:

```text
mid_heading = theta + d_theta / 2
x += d_center * cos(mid_heading)
y += d_center * sin(mid_heading)
theta = normalizeAngle(theta + d_theta)
```

When both wheels move equally, `d_theta` should be zero. When they move equal
amounts in opposite directions, `d_center` should be zero. These are useful quick
checks for the signs in the equations.

The node publishes an odometry message, but it does not publish TF. Lesson 7 owns
`odom -> base_footprint` through the EKF.

In `publishOdometry`, fill these fields deliberately:

- copy the measurement time into `header.stamp`
- set `header.frame_id` to `odom` because the pose is expressed in odom
- set `child_frame_id` to `base_footprint` because the twist describes the robot
- write `x` and `y` into the position
- turn yaw into a quaternion with `tf2::Quaternion::setRPY(0, 0, theta)` and
  `tf2::toMsg`
- write forward speed to `twist.twist.linear.x` and turn rate to
  `twist.twist.angular.z`

Set small, nonzero covariance entries for x, y, yaw, forward velocity, and yaw
rate. Covariance arrays are flat row-major 6-by-6 arrays ordered x, y, z, roll,
pitch, yaw, so the diagonal indices used here are 0, 7, and 35.

The yaw-to-quaternion part should look like this:

```cpp
tf2::Quaternion q;
q.setRPY(0.0, 0.0, theta_);
odom.pose.pose.orientation = tf2::toMsg(q);

odom.twist.twist.linear.x = vx;
odom.twist.twist.angular.z = wz;
odom_pub_->publish(odom);
```

## CMake And Component Registration

After the skeleton compiles conceptually, wire the package:

- build a shared library for the node
- register it with `rclcpp_components_register_node`
- also install a standalone executable so `ros2 run wheel_odometry wheel_odometry`
  works for parameter experiments
- install the launch directory

The C++ source should end with component registration for `WheelOdometry`.

The component registration name must exactly match the fully qualified C++ class
name used by the launch file, including its namespace. In `CMakeLists.txt`, the
key sequence is: `find_package(...)`, `add_library(... SHARED ...)`,
`ament_target_dependencies(...)`, `rclcpp_components_register_node(...)`, and
`install(...)`. Registering with the `EXECUTABLE wheel_odometry` option creates
the standalone `ros2 run` entry point as well as the loadable component.

After both the header and source file exist, use this complete CMake target shape:

```cmake
add_library(wheel_odometry_component SHARED src/wheel_odometry.cpp)
ament_target_dependencies(wheel_odometry_component
  rclcpp rclcpp_components sensor_msgs nav_msgs geometry_msgs
  tf2 tf2_geometry_msgs robonav_training_common)
rclcpp_components_register_node(wheel_odometry_component
  PLUGIN "robonav_training::WheelOdometry"
  EXECUTABLE wheel_odometry)

install(TARGETS wheel_odometry_component
  ARCHIVE DESTINATION lib
  LIBRARY DESTINATION lib
  RUNTIME DESTINATION bin)
install(DIRECTORY launch DESTINATION share/${PROJECT_NAME})
```

Above that target, add `find_package(... REQUIRED)` for every dependency listed
in `ament_target_dependencies`, plus `ament_cmake`, and add
`include_directories(include)`. Leave the generated `ament_package()` as the last
command. The [CMake/package reference](../reference/cmake-package.md) explains
each line if this is your first CMake file.

## Launch File

Write `wheel_odometry.launch.py` so it loads the composable node into its own
`component_container` and sets `use_sim_time: true`.

The `ComposableNode` needs the package name, the exact registration/plugin name,
the node name, and a parameters list. Declare `use_sim_time` as a launch argument
and pass its `LaunchConfiguration` to the component. This keeps the launch file
usable in simulation while allowing `use_sim_time:=false` on a real robot.

## Build Before Running

From `/workspace`, build just this package and source the new overlay:

```sh
colcon build --symlink-install --packages-select wheel_odometry
source install/setup.bash
ros2 pkg executables wheel_odometry
```

The final command should list the standalone executable. If ROS cannot find the
package after a successful build, the usual cause is forgetting to source
`install/setup.bash` in that terminal. Rebuild and re-source after changing C++,
CMake, package metadata, or launch files.

## Acceptance Checks

Run the simulator and this node in separate sourced terminals:

```sh
ros2 launch robonav_training_bringup sim.launch.py
ros2 launch wheel_odometry wheel_odometry.launch.py
ros2 topic echo /wheel/odometry
ros2 run teleop_twist_keyboard teleop_twist_keyboard
```

Expected behavior:

- `/wheel/odometry` exists
- `child_frame_id` is `base_footprint`
- `header.frame_id` is `odom`
- moving forward changes x
- spinning changes yaw
- no `odom -> base_footprint` TF appears yet

If the topic exists but never updates, inspect the input first with
`ros2 topic echo /joint_states --once` and confirm the two configured joint names
and the `position` array are present. If forward motion changes y or spinning
changes x significantly, recheck the midpoint equations, wheel ordering, and the
sign of `d_theta`.
